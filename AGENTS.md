- Admin 2-step verification is remembered per browser and account for a limited time (src/lib/adminOtp.ts) and cleared on sign-out; it is only a UI gate, and real admin access is enforced by database roles. Why: being asked to verify again in every tab, refresh or return visit was locking admins out.
- Admin "사이트 설정" is stored in the site_settings table and read through src/hooks/useSiteSettings.ts; menu and category names typed by admins are shown as typed (automatic translation was removed with the Lovable AI service). Both need migration 20261010030000 applied, and fall back to defaults / the typed name until it is. Why: the settings screen used to save only to the admin's own browser and had no effect on the store.
- Admin roles belong to one owner account only (migration 20261012010000): the role is granted automatically when the owner address in private.owner_email() (youthroom.shop@gmail.com, set by migration 20261014010000) signs in with a verified email, and the database rejects admin roles for any other account. Why: the old grant-admin function let anyone become admin without signing in, so it was removed.
- The backend is the owner's own Supabase project (wlqulztkqjbzmrfhyggv), not Lovable Cloud; Google sign-in uses Supabase auth directly and the site is deployed on Vercel at youthroom.shop. Why: the store was moved off the Lovable-managed database.
- Design mode is the editor at /admin/design (src/pages/AdminDesign.tsx): it previews the real storefront in a frame, and "게시하기" saves to site_settings.settings.design, which src/components/DesignApplier.tsx applies on every non-admin page. Only add a control there if the storefront actually reads it (src/lib/design.ts). Why: the old design mode saved to the admin's browser only and changed nothing on the site.
- Coupons are checked at checkout through the validate_coupon database function (migration 20261012020000), because customers cannot read the coupons table; each order with a coupon increments used_count. Why: coupons could be created in admin but never used.
- Product, banner, menu and category text typed by admins is shown as typed when no translation exists; AI auto-translation depended on Lovable and no longer runs. Why: untranslated banners were silently hidden from the home page.
- Popups, corner style, hero/featured layout, header options and custom CSS are all part of the design in src/lib/design.ts; popup code (HTML/JS) is rendered by src/components/PopupHost.tsx inside a sandboxed frame. Why: admin-written scripts must not be able to break or read the store page.
- Store prices are US dollars (formatPrice in LanguageContext), so admin screens show amounts with "$", and shipping_rates.fee is in dollars too. Why: the admin used to label every amount "원", which made dollar amounts look like won.
- Admin pages have their own theme: DesignApplier sets the admin-theme class on <html> for /admin routes (variables in src/index.css) and loads the Pretendard font, so style admin screens with the shared tokens (bg-card, text-muted-foreground, primary) rather than storefront colors. Why: the admin used to inherit the storefront's pale pink theme and serif headings and was hard to read.
- The home page is a free list of blocks stored in site_settings.settings.design.home.blocks. Each block type is defined once in src/lib/homeBlocks.ts (defaults, validation and the editor form all come from that definition), rendered by src/components/home/HomeBlocks.tsx and edited in src/components/admin/design/BlockEditor.tsx; to add a widget, add a type there and a case in HomeBlocks. Blocks with no content are skipped on the live site. Why: the home page used to be three fixed sections that could only be reordered or hidden.
- Blocks can also surround other pages (products, ranking, contact, Q&A): each page list in design.pages holds one fixed "pageContent" block, and <PageBlocks page part="top|bottom" /> in the page renders the blocks before / after it. A block's width (out of 12) puts neighbouring narrow blocks side by side on PC. In the editor preview, blocks post messages to the editor for select, drag-to-move and drag-to-resize (names in src/lib/homeBlocks.ts). Why: owners wanted to arrange widgets like a site builder without touching page code.
- Each publish keeps the replaced design in site_settings.settings.designHistory (last 10) so it can be restored from the editor's 고급 tab.
- vercel.json rewrites every path to index.html because the app routes in the browser; without it, opening or refreshing any inner page on Vercel (/products, /admin, and /auth after Google sign-in) returns 404. Real files (assets, sitemap.xml, robots.txt) are still served as files.
- Email goes out through Resend from the verified youthroom.shop domain (EMAIL_FROM secret) and the shop inbox is youthroom.shop@gmail.com (ADMIN_NOTIFY_EMAIL secret): it receives inquiry notices, is the reply-to on customer emails, and gets a copy of welcome and inquiry-reply emails (copyToAdmin in supabase/functions/_shared/email-templates/send.ts). Why: the owner wants every customer conversation to land in one inbox.
- The beauty consultation recommends products by the consult_tags each product is given in the product editor (뷰티 상담 추천: concern IDs plus one skincare type); matching lives in src/lib/consultation.ts and the IDs must stay in step with the options in BeautyConsultation.tsx. Why: the AI recommender depended on Lovable and did not work; the owner wants to decide which products are recommended.
- Uploaded images are resized in the browser (fitImageWithinLimit in src/components/admin/ImageUploader.tsx): product main and gallery images become exactly 1200x1200 with the whole picture on white (never cropped), other images are only scaled down. Why: product photos must look uniform across the store.
- Payment is bank transfer only: an order is created as "pending" (shown as 입금 대기 / Awaiting payment) and becomes "confirmed" (결제 완료 / Payment confirmed) only when the admin presses 입금 확인 in 주문 관리, which also emails the customer. Bank details live in payment_settings (admin-only; customers read them through get_checkout_payment_info()). Seller details for the footer live in site_settings (사이트 설정 > 사업자 정보).
- The Q&A page reads its questions, answers, font and colors from site_settings.settings.faq (edited in admin FAQ 관리, src/lib/faq.ts); until an admin saves, it shows the texts from the qa_* translation keys.
- The contact page and support chat only accept inquiries from signed-in members (send-inquiry requires a session, phone and an inquiry type); the contact form lets members attach one of their orders and a product from it.
- Categories are two levels (parent_id). Skincare has 스킨/토너, 에센스/세럼/앰플, 크림, 미스트/오일, 마스크팩 and Makeup has 립/베이스/아이 (migration 20261015000000). A top category filter includes its subcategories (src/lib/categoryTree.ts), and a skincare subcategory slug is that product's routine step in the beauty consultation (SKIN_STEPS in src/lib/consultation.ts) — keep those slugs.
- All product lists use PRODUCT_GRID (src/lib/productGrid.ts, up to 5 per row). The Ranking view of the shop and the "랭킹" home block show TOP 1-3 framed and larger (ProductCard rank prop); ranking order is manual_rank (랭킹 관리) then review count.
